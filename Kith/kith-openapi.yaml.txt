openapi: 3.1.0

info:
  title: Kith API
  version: 1.0.0
  description: |
    Kith is a multi-workspace platform for coordinating family and community financial
    contributions, tasks, and events.

    ## Authentication
    Most endpoints require a Supabase-issued Bearer JWT, supplied as
    `Authorization: Bearer <access_token>`.
    The `POST /v1/auth/refresh` endpoint additionally reads the `refresh_token`
    HttpOnly cookie that is set automatically on login / token refresh.

    ## Response Envelope
    **Success** responses always use the shape:
    ```json
    { "data": { ... }, "meta": { "pagination": { ... } } }
    ```
    `meta` is omitted when there is no pagination or extra metadata.

    **Error** responses always use the shape:
    ```json
    { "error": { "code": "ERROR_CODE", "message": "Human-readable description" } }
    ```

    ## Role Notation
    Endpoint descriptions annotate access as **[Public]**, **[Authenticated]**,
    **[Member]** (requires active workspace membership), or **[Admin]** (requires
    `role = admin` in the target workspace).

    ## Idempotency
    `POST /v1/workspaces/{workspaceId}/containers/{containerId}/ledger` supports the
    optional `X-Idempotency-Key` request header (UUID per submission) for exactly-once
    contribution recording. Requires a DB migration to activate (see code comments).

# SPEC ANALYSIS EXTENSION
# ════════════════════════════════════════════════════════════════════
x-analysis:
  missing_endpoints:
    - >
      Ledger validator schemas for createLedgerEntrySchema, updateLedgerEntrySchema,
      createTaskSchema, bulkCreateTasksSchema, etc. were not provided as separate
      files. Field-level constraints for those schemas were inferred from controller
      code and are accurate but less precise than direct validator inspection.
    - >
      No endpoint exists to refresh a single container's public_token (revoke and
      regenerate). Currently callers can only generate, not revoke.
    - >
      No endpoint to list or search milestones independently — only GET by ID or
      the merged timeline. A GET /milestones list endpoint would be useful.
    - >
      No endpoint to re-send an invite notification email after creation.
    - >
      GET /v1/workspaces/:workspaceId/containers/:containerId/ledger/:entryId/proof-url
      only accepts a query param `file_index` (default 0). There is no endpoint to
      get a download URL for task proof files by index (only upload/confirm/delete
      are present).

  inconsistencies:
    - >
      GET /v1/notifications uses a `resolveMember` middleware that requires the
      user to have at least one active workspace membership. If a user has no
      memberships (e.g. freshly registered), all notification endpoints will return
      404 rather than an empty list, which may surprise clients.
    - >
      POST /v1/auth/refresh reads the refresh token exclusively from the HttpOnly
      cookie (`req.cookies.refresh_token`). The auth validator defines a
      `refreshTokenSchema` with a `refresh_token` body field, but this field is NOT
      read by the controller — only the cookie is used. The body field is dead code.
    - >
      The response envelope in response.js is `{ data: {...}, meta: {...} }` — there
      is NO top-level `success` boolean. Some clients or SDK generators may expect
      the conventional `{ success: true, data: {...} }` pattern.
    - >
      `DELETE /v1/workspaces/:workspaceId/containers/:containerId/tasks/:taskId`
      returns 204 No Content, while most other delete endpoints return 200 with
      a `{ message }` body. The pattern is inconsistent within the same API.
    - >
      `DELETE /v1/workspaces/:workspaceId/groups/:groupId/members/:memberId` also
      returns 204 with no confirmation message, unlike most other admin deletions.
    - >
      The legacay `/v1/invites/:token/preview` and `/v1/invites/:token/accept`
      routes duplicate `/v1/public/invites/:token` and `/v1/public/invites/:token/accept`
      with no redirect. Both are active simultaneously.

  suggestions:
    - >
      Add a standard `success: boolean` field to the response envelope for SDK
      compatibility: `{ success: true, data: {...}, meta: {...} }` — the change
      is backwards-compatible if clients ignore unknown fields.
    - >
      Standardise all delete responses to either 204 (no body) or 200 with
      `{ message }`. Choose one convention across the entire API.
    - >
      Add `GET /v1/workspaces/:workspaceId/milestones` list endpoint with date
      range filtering and pagination.
    - >
      Consider adding `POST /v1/workspaces/:workspaceId/containers/:containerId/revoke-public-link`
      to let admins invalidate shared links.
    - >
      The 10-minute duplicate guard on ledger entry creation is a server-side
      heuristic that can fire on legitimate re-submissions (e.g. after a network
      error). Consider making the `X-Idempotency-Key` header the primary
      deduplication strategy and relaxing the time-window guard to admin-configurable.
    - >
      Expose the `notification_worker.js` and `data_export_worker.js` queue
      job status via a simple `GET /v1/auth/data-export/status` endpoint so
      clients can poll without waiting for an email.
    - >
      The Bull Board admin UI at `/admin/queues` is not documented here as it is
      an internal ops tool, not a consumer API endpoint.
